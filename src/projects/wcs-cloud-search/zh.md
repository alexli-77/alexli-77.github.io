![系统架构](/assets/projects/wcs-cloud-search/architecture.svg)

## 背景

58 是分类信息（Listing）业务：房产、招聘、二手车、本地服务……每条业务线都要有自己的垂直搜索。早期的做法是每条业务线单独部署一套搜索，带来的问题很具体：

- 系统多、版本多，内核升级要一套一套地追，没人能说清线上到底跑着几个版本；
- 新业务想要搜索，得从机器申请、索引构建到上线走一遍，周期按周算；
- 机器按业务独占，低峰业务的资源大量闲置。

云搜索要做的，就是把"搭一套搜索"变成"在平台上申请一个应用"：资源统一调度，内核统一升级，业务只管 schema 和查询。

## 架构

整体分成数据面和控制面，全部组件跑在 Kubernetes 上。

**接入层：wcs-agent SDK。** 业务方嵌入的客户端 jar，提供仿 Elasticsearch 的查询 DSL（bool / term / range / geo / 聚合 / 排序 / 高亮 / suggest），支持同步、异步和批量写入，内部转成内核的 Protobuf 请求，经 58 的 SCF RPC 发出。

**路由层：route proxy。** 只做分发：根据 appId 查路由表，按权重选出索引版本和所在集群，转发给该集群的下沉 proxy。它本身无状态、多副本部署，不绑定某个集群，可以跑在 4 个集群中的任意一个，按流量独立扩缩。同一个镜像按环境变量跑成 query 或 index 两种模式。附带按应用、按方法采样的流量复制，用于新版本预热。

**集群层（×4）：下沉 proxy + 内核。**
- query proxy：把 DSL 解析成内核查询，做分词、查询黑名单过滤，把请求发给 merger；结果回来后从 Wtable 批量回填存储字段。
- index proxy：校验 schema 和 CAS 版本，先写 Wtable（文档的唯一真相源），再把变更双写到两套 Kafka。
- merger 负责把查询扇出到各分片并合并排序；每个 searcher pod 里是自研 C++ 倒排内核加一个 builder sidecar。文档按 murmur3(id) mod N 分片。

**数据管道。** builder 有两种模式：INST 消费 Kafka 做增量，MAIN 从 Wtable 的 HDFS 快照做全量重建。文本字段交给 edoc 分词服务（无状态，接内部 cutword 和 NLP 模型），转成内核的索引 Protobuf 后写入本地内核。builder 重启时根据内核的 segment 日志定位 Kafka offset 回放，保证不丢更新。

**控制面：wcs-manager。** Vue + Spring Boot 的管理平台，管理应用从申请到下线的完整生命周期：
- 应用和字段走审批，审批通过后自动分配 Kafka topic 和 Wtable 存储；
- 部署时用版本化的 YAML 模板渲染出每个分片的 Deployment / Service，通过 fabric8 直接下发到对应 K8s 集群，分批滚动，支持扩缩容、灰度和回滚；
- 路由表、schema、分词词典推到配置中心（WConfig），merger 的分片列表写 etcd，proxy 热加载，不重启；
- 监控走 Micrometer → Kafka、Prometheus 和 ES，告警通过短信 / 电话 / 微信送达。

## 关键设计

**1. 两层 proxy：分发和业务逻辑分开。**

![两层 proxy 路由](/assets/projects/wcs-cloud-search/routing.svg)

路由 proxy 只回答"这个请求去哪个集群、哪个版本"；下沉 proxy 只关心"这个请求怎么查、怎么写"。拆开以后，灰度发布、版本回滚、应用在集群间迁移，都变成配置中心里改一个权重，业务方的调用代码不用动。route proxy 无状态，副本可以放在任意集群，某个集群整体故障时，其他集群里的副本照常转发；下沉 proxy 跟着自己的集群走，可以按集群独立升级，一个集群出问题不会拖累其他集群。

**2. 读写分离，Wtable 做真相源。**

写入先落 Wtable，再通过 Kafka 异步进索引。好处是索引可以随时从 Wtable 快照全量重建，增量链路出问题时能兜底；查询只从内核拿 docId 和排序值，存储字段从 Wtable 回填，内核的内存只留给倒排和排序属性。

**3. 应用生命周期全自动化。**

一个应用从申请、审批、分配资源、部署、灰度、上线到下线，状态全部记在 MySQL 里，由 manager 驱动 K8s 完成。上线前要经过流量复制预热和 diff test，全量重建走审批工单。业务方接入只需要定义 schema、调 SDK。

**4. 分词服务独立出来。**

分词是 CPU 密集且依赖模型和词典的，和内核放在一起会互相抢资源、升级也绑在一起。拆成无状态的 edoc 服务后可以单独扩容，词典按应用版本化管理，改词典不用重启内核。

## 结果

- **接入快**：业务接入搜索从"单独搭一套"变为在平台上申请应用，分钟级完成；
- **资源省**：多租户混部替代按业务独占机器，机器 CPU / 内存利用率动态维持在 80% 以上，同时保证流量负载均衡；
- **迁移无损**：利用 K8s 多副本，配合数据重建机制和流量路由，单个副本可以无损迁移，节点维护和扩缩容不影响业务；
- **规模与稳定性**：从 0 到 1 建成 4 个线上集群、396 台服务器，承接公司 300+ 个线上业务，峰值 QPS 20 万+，公司核心业务长期稳定运行。

## 回头看

如果今天重做，我会改这几处：

- **路由信息有三个来源。** route proxy 读 WConfig，下沉 proxy 轮询 MySQL，merger 读 etcd，三者的一致性靠 manager 按顺序写入来保证。我会收敛到一个带版本号的路由源。
- **写入链路靠同步等待。** index proxy 双写 Kafka 时阻塞 RPC 线程等两边回调，Kafka 端 acks=1、不重试，一致性实际上依赖 Wtable 兜底和全量重建。我会改成异步确认，再加一个 Wtable 和索引之间的对账任务。
- **proxy 层没有限流和熔断。** 保护主要靠 RPC 超时和摘除异常节点。多租户场景下，一个业务的突发流量可能挤占整个集群，应当按 appId 做配额。
